# 위키 프로젝트 문서 채점 기준 v0

> 2026-11-15 작성. 이슈 #14(상태 대시보드)의 채점 엔진 초안. 대상은 개발자 본인 경력 위키의 프로젝트·장애 문서.
> 직군별 분기(#16)는 아직 반영하지 않았다 — 이 v0은 백엔드 기준이다.

## 판정 원칙

- **기준은 "면접에서 버틸 만큼 충분한가"다.** 제목이나 문장이 있다는 것만으로는 채움이 아니다(2026-11-15 사용자 결정).
- **문서 구조에 의존하지 않는다.** 본인 위키는 문서마다 H2 구성이 다르다(38개 문서 공통 절은 `주의`·`관련 문서`·`근거`뿐). 칸마다 문서 **전체**에서 해당 내용을 찾고, 찾은 위치(절 이름)를 근거로 적는다.
- **`주의` 절도 읽는다.** 본문이 주장한 것을 `주의`가 한정·부정하면 `주의` 쪽을 따른다.

## 판정 4단계

| 판정 | 조건 | 점수 |
|---|---|---|
| 충분함 | 아래 칸별 "충분함" 조건을 모두 만족 | 1 |
| 부족함 | 해당 내용이 있으나 조건 일부를 못 채움 | 0.5 |
| 비어 있음 | 해당 내용이 문서 어디에도 없음 | 0 |
| 한계 명시 | 해당 내용이 **없고**, 문서가 그 내용을 "확인할 수 없다/기록이 없다"고 **명시** | 분모에서 제외 |

- 내용이 일부라도 있으면 한계 명시가 아니라 충분함/부족함으로 판정한다. 한계 명시는 "없음 + 없다는 명시"일 때만이다.
- 채움률 = 점수 합 ÷ (7 − 한계 명시 칸 수) × 100. 한계 명시를 0점으로 치면 퍼센트를 올리려고 확인 안 된 것을 지어내는 유인이 생긴다.
- 부족함·비어 있음 판정에는 반드시 **이유 한 줄**과 **채우기 질문 하나**를 붙인다(대시보드와 `/status` 채우기 흐름이 이걸 그대로 쓴다).

## 7개 칸

| # | 칸 | 충분함 조건 | 부족함의 전형 |
|---|---|---|---|
| C1 | 어떤 문제였나 | 구체적 증상 + 영향(누가·무엇이·얼마나 불편/위험했나) + 왜 지금 풀어야 했나 | 위험만 일반론으로 서술, 기능의 출발점(누가 왜 요청했나)이 없음 |
| C2 | 내가 한 일 | 본인 행동이 구체적이고, **본인 범위와 팀·타인 범위가 구분**돼 있다 | 작업 목록은 있으나 주어가 없어 본인 몫인지 알 수 없음 |
| C3 | 문제 해결 방식 (구조화) | 원인을 쪼갠 흔적 또는 **대안과 선택 이유**(트레이드오프)가 있다 | 최종 설계만 있고 "왜 다른 방법이 아니라 이것인가"가 없음 |
| C4 | 측정 방식 정의 | 결과 지표를 **무엇을·어떤 조건에서·무엇을 분모로** 쟀는지 정의돼 있다 | 수치 출처만 있고 측정 조건·분모가 없음. 테스트(검증 절차)는 있으나 성과 측정 정의는 없음 |
| C5 | 결과 KPI | before→after 수치. 노력량(커밋 수·라인 수·소요일)은 KPI가 아니다 | 정성 결과만, 한쪽 값만, "수 일→수 시간"처럼 정밀하지 않은 값 |
| C6 | 왜 대단한가 | 난이도·리스크·규모를 **비교 맥락**과 함께 설명(실패하면 무슨 일이 났나, 무엇이 어려웠나) | "중요했다" 수준의 주장만 있음 |
| C7 | 데이터 문해력 | 판단을 데이터로 내렸거나, 데이터 해석의 함정(분모 오염·상관≠인과·합산 수치)을 인지하고 다뤘다 | 근거 위생(출처 표기)만 있고 데이터에 기반한 판단은 없음 |

## 출력 형식 (채점자 공통)

```
## <문서명>
| 칸 | 판정 | 근거 위치 | 이유 (부족·비어 있음이면 필수) | 채우기 질문 (부족·비어 있음이면 필수) |
|---|---|---|---|---|
| C1 | ... | ... | ... | ... |
...
채움률: N% (점수 합 X / 분모 Y)
```

## v0에서 알려진 약점 (채점 전 예측)

- C7(데이터 문해력)은 정의가 가장 흐리다 — 채점자 간 불일치가 가장 클 것으로 예측
- C2는 "본인 범위 구분"을 얼마나 엄격히 보느냐에 따라 갈릴 것으로 예측
- 가중치는 전 칸 동일(1/7). KPI와 다른 칸의 무게가 같은지는 미결
