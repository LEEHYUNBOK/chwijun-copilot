# 위키 문서 채점 기준

기준 v4 (2026-11-15). 검증 기록: 리포 `docs/status-dashboard/`. 괄호 속 `(v4 #1)` 같은 표기는 그 기록의 개정 번호다.

## 판정 원칙

- 기준은 **"면접에서 버틸 만큼 충분한가"**다. 제목이나 문장이 있다는 것만으로는 채움이 아니다.
- 문서 구조에 의존하지 않는다. 칸마다 문서 **전체**에서 해당 내용을 찾고, 찾은 위치(절 이름)를 근거로 적는다.
- `주의` 절도 읽는다. 본문이 주장한 것을 `주의`가 한정·부정하면 `주의` 쪽을 따른다.
- **문서에 쓰인 수치를 그대로 믿지 않는다.** 출처·조건을 문서 안에서 되짚을 수 없는 수치는 충분함의 근거가 되지 못한다.
- 문서 안의 링크는 열지 않는다. 판정은 문서에 쓰인 내용만으로 내린다.
- **칸을 보기 전에 문서 유형을 정한다 (v4 #1).** 문서의 중심이 무엇인지로 하나만 고른다.
  - **프로젝트** — 무언가를 만들거나 고친 작업이 중심인 문서(사고가 계기여도 본문이 만든 것·고친 것이면 프로젝트)
  - **장애** — 서비스 중단·오류 사고의 경위·원인·대응이 중심인 문서
  - **조사** — 사실 확인·측정·비교·감사가 중심이고, 결과가 "무엇이었나/어떤 수준인가"인 문서(부하 테스트로 현 수준을 잰 문서 포함)
  - **제외** — 경력 소재가 아닌 문서: 목차·개요·정정 이력·프로필·지원현황 트래커·브랜드 가이드·작성 규칙. 칸을 채점하지 않는다

## 판정 4단계

| 판정 | 조건 | 점수 |
|---|---|---|
| 충분함 | 칸별 "충분함" 조건을 모두 만족 | 1 |
| 부족함 | 칸별 "부족함" 조건에 해당 | 0.5 |
| 비어 있음 | 칸별 "비어 있음" 조건에 해당하거나, 해당 내용이 문서 어디에도 없음 | 0 |
| 한계 명시 | 해당 내용이 **없고**, 문서가 그 내용을 "확인할 수 없다/측정하지 않았다"고 **명시** | 분모에서 제외 |

- 부족함과 비어 있음은 아래 칸별 조건으로만 가른다. "내용이 일부라도 있으면 부족함"이 아니다.
- **한계 명시는 작성자 본인의 작업에 대해서만 (v4 #2):** "내가 측정하지 않았다/확인할 수 없었다"처럼 문서 작성자 쪽 작업의 내용이 없다고 밝힌 경우만 인정한다. "이 설정을 왜 골랐는지 기록에 없다"처럼 타인의 과거 결정에 대한 공백은 한계 명시가 아니다 — 해당 칸은 문서에 있는 내용으로 판정한다.
- **한계 명시는 칸 단위 (v3 #1):** 문서의 한계 문장이 **어느 칸의 내용**이 없다고 말하는지 보고, 그 칸에만 한계 명시를 준다. 한 문장으로 두 칸을 동시에 한계 명시로 만들지 않는다(그 문장이 두 칸의 내용을 각각 명시적으로 부정할 때만 예외). 문서 주제의 일부 구간에만 걸린 한계 문장은 그 칸 전체의 한계 명시가 아니다.
- **C5 한계 명시 범위 (v2 #2):** 주 KPI가 없다고 명시했을 때, 문서에 남은 수치가 운영 효과 KPI가 아니면(검증 결과·벤치마크·구조 수치·노력량) 한계 명시로 본다. 남은 수치가 운영 효과 KPI면(전 값만 있는 경우 포함) 한계 명시가 아니라 그 수치로 충분/부족을 판정한다.
- **채움률·점수 합·퍼센트를 계산하거나 쓰지 않는다.** 스크립트가 판정에서 계산한다.

## 7개 칸

| # | 칸 | 충분함 | 부족함 | 비어 있음 |
|---|---|---|---|---|
| C1 | 어떤 문제였나 | 구체적 증상 + 영향(누가·무엇이·얼마나) + 왜 지금 풀어야 했나 | 증상은 있으나 영향의 크기나 "왜 지금" 중 하나가 없음 / 위험을 일반론으로만 서술 | 문제 서술 없음 |
| C2 | 내가 한 일 | **① 본인 범위와 팀·타인 범위를 가르는 문장**이 있고, **② 주어(본인)가 드러난 본인 행동이 1개 이상** 있다 — 둘 다 필요 | 행동은 구체적이나 주어가 없어 본인 몫을 알 수 없음 / 범위 경계 문장만 있고 본인 행동 문장이 없음 / 본인 행동은 있으나 팀 몫과의 경계가 없음 | 행동 서술 없음 |
| C3 | 문제 해결 방식 | **당시 고를 수 있었던 다른 안 하나 이상**과, 그 안을 버리고 이 방식을 고른 이유(트레이드오프)가 있다 | 선택 이유나 원인 분해는 있으나 **대안 비교가 없음** — "다른 방법은요?"에 답할 수 없음. **"기존 방식은 불가능했다"만 있는 경우**, **이전 구현의 문제 → 새 구현만 있는 경우**, **"검토 중"인 대안만 있는 경우**도 여기 | 최종 설계만 있고 이유도 없음 |
| C4 | 측정 방식 정의 | 결과 지표를 **무엇을·어떤 조건에서(기간·대상)·무엇을 분모로** 쟀는지 정의돼 있고, 출처를 문서 안에서 되짚을 수 있다 | 지표는 정의됐으나 조건·분모·출처 중 일부가 없음 / **분모가 맞지 않고 해명이 없음** / **현황 수치(사용량·규모)만 정의되고 결과 지표의 측정 정의는 없음** | **검증 절차(테스트·체크리스트)만 있고 성과 측정 정의는 없음** / 측정 서술 없음 |
| C5 | 결과 KPI | 운영 효과 KPI가 **before→after 둘 다** 있고, 각 수치의 출처를 되짚을 수 있다 | 운영 효과 KPI이지만 한쪽 값만 있음 / 값이 정밀하지 않음("수 일→수 시간") / 출처를 되짚을 수 없음 | **정성 결과만** / **구조·산출물 수치만**(파일·화면·테이블 수) / **노력량만**(커밋·라인 수·소요일) |
| C6 | 왜 대단한가 | 난이도·리스크·규모를 **비교 맥락**과 함께 설명(실패하면 무슨 일이 났나, 무엇이 어려웠나) | "중요했다" 수준의 주장, 또는 가정적 위험만 있고 난이도·규모가 없음 | 서술 없음 |
| C7 | 데이터 문해력 | **데이터를 보고 내린 결정**과 그 데이터가 있다(예: 회귀 결과 N건 중 N건 통과를 보고 배포 결정, 로그 분포를 보고 임계값 설정). 데이터와 다른 이유가 섞였다면 **둘을 어떻게 저울질했는지**가 적혀 있어야 한다 | 데이터 기반 결정은 없으나 **해석 함정을 인지하고 다룸**(분모 오염·합산 수치·상관≠인과) / 데이터는 제시됐으나 결정 이유가 데이터 외 이유뿐 | 둘 다 없음. 출처 표기(근거 위생)만 있는 경우 포함 |

### 문서 유형별 읽는 법 (v4 #1)

위 표가 **프로젝트** 유형의 기본이다. 장애·조사 유형은 아래 행이 C1·C3·C4를 대신한다. C2·C5·C6·C7은 모든 유형에서 위 표 그대로다.

| 유형 | 칸 | 충분함 | 부족함 | 비어 있음 |
|---|---|---|---|---|
| 장애 | C1 | 증상 + 영향 범위(무엇이·얼마나·얼마 동안) + 원인 | 증상·영향은 있으나 원인이나 영향의 크기 중 하나가 없음 | 사고 서술 없음 |
| 장애 | C3 | 원인 분해 + **대응·재발방지에서 고를 수 있었던 다른 안과 버린 이유** | 원인 분해만 / 대책만 나열 / "검토 중"인 안만 | 대응 서술 없음 |
| 장애 | C4 | 발생·감지·복구 시각과 그 출처 **+ "발생"·"복구"를 무엇으로 판정했는지** | 시각·지속 시간만 있고 판정 기준이 없음 / 출처 일부 없음 | 시각 서술 없음 |
| 조사 | C1 | **무엇이 불확실했나** + 그 불확실성이 어떤 판단(서술·결정·위험)에 영향을 주나 | 조사 대상은 있으나 왜 확인해야 했는지가 없음 | 없음 |
| 조사 | C3 | 확인 방법 + **다른 확인 방법과 그 방법을 버린 이유**(예: 저장소로는 구분 불가 → 콘솔 직접 조회) | 확인 방법만 있음 | 확인 방법 서술 없음 |
| 조사 | C4 | 조사 대상·**시점**·분모·출처가 있음. 부하 테스트면 표본 규모까지 | 일부 없음 | 없음 |

- **벤치마크 수치는 유형과 무관하게** C4 근거로 쓸 때 표본 규모(반복 횟수·요청 수)가 있어야 충분함이다. 프로젝트 문서의 구성 간 비교도 같다.
- 유형이 애매하면 "애매했던 이유"에 적고, 문서의 **본문 분량이 가장 많은 쪽**으로 고른다.

### C4·C5 감점 귀속

같은 수치의 결함을 두 칸에서 이중으로 깎지 않는다.

| 결함 | 깎는 칸 |
|---|---|
| 값이 정밀하지 않음, 한쪽 값만 있음 | C5만 |
| 측정 조건(기간·대상)·분모가 없음 | C4만 |
| 출처를 되짚을 수 없음 | C4·C5 각각 상한이 부족함 |

### C5 내용 유형 예시

⚠️ 첫 행의 수치는 형식을 보여주려고 만든 **가상 예시**다.

| 서술 | 유형 | C5 판정 |
|---|---|---|
| "온보딩 3일 → 2시간 (기간 X, 신규 기관 N곳, 요청~완료 시각 기준)" | 운영 효과 KPI, 양쪽 값, 출처 있음 | 충분함 후보 |
| "온보딩 수 일 → 수 시간" | 운영 효과 KPI, 정밀하지 않음 | 부족함 |
| "동시 40명에서 응답 약 10초, 해결 후는 측정 안 함" | 운영 효과 KPI, 전 값만 | 부족함 (한계 명시 아님) |
| "화면 6개 → 공통 컴포넌트 1개" | 구조·산출물 수치 | 비어 있음 |
| "커밋 72건, 2주 소요" | 노력량 | 비어 있음 |
| "DB 주도로 전환됐다" | 정성 결과 | 비어 있음 |
| "구성 A vs 구성 B 부하 테스트 — P99 지연 X ms vs Y ms" | 구성 간 벤치마크 | 비어 있음 (C4·C7 근거로는 인정) |
| "재처리 N건 중 M건 결과 변경" | 검증 결과 | 비어 있음. 주 KPI 없음을 명시했다면 C5 한계 명시 |

## 출력 형식

문서 하나당 아래 형식 그대로 쓴다. 스크립트가 이 형식을 읽어 검증한다 — 줄 모양을 바꾸지 않는다. `<문서명>`은 위키 폴더 기준 파일 경로에서 `.md`를 뺀 것이다(예: `배포-실측`). 다른 이름을 쓰면 기록이 거부된다.

```
## <문서명>
유형: <문서명> = 프로젝트|장애|조사
| 칸 | 판정 | 근거 위치 (절 이름) | 이유 | 채우기 질문 |
|---|---|---|---|---|
| C1 | 충분함 | 「배경」 | - | - |
| C2 | 부족함 | 「주의」 | <왜 부족한가 한 줄> | <이 칸을 채우려면 사용자에게 물을 질문 하나> |
...(C7까지)
판정: <문서명> = 충,부,비,한,부,충,부
```

- 판정 표의 단어는 `충분함`·`부족함`·`비어 있음`·`한계 명시` 넷 중 하나. 판정 줄 기호는 순서대로 `충`·`부`·`비`·`한`, C1부터 C7까지 7개
- 부족함·비어 있음 칸은 이유와 채우기 질문이 **둘 다 필수**. 충분함·한계 명시 칸은 `-`
- 채우기 질문은 사용자가 기억·자료로 답할 수 있는 구체적 질문 하나("측정 기간과 대상은?")
- 유형이 `제외`면 표와 판정 줄 없이 두 줄만 쓴다:

```
유형: <문서명> = 제외
제외 이유: <한 줄>
```

### 출력 규칙 — 사람 이름·식별자 금지

- 이유·근거 위치·채우기 질문에 **사람 이름을 쓰지 않는다.** 문서에 이름이 있어도 "담당 팀원", "팀원", 문서에 이미 쓰인 별칭으로만 부른다
- **회사명·티켓 번호·테이블명·코드 식별자(클래스·메서드명)도 인용하지 않는다.** 근거 위치는 **절 이름**으로만 가리킨다(예: 「설계 판단」). 내용을 설명해야 하면 일반어로 바꾼다(예: "메뉴 테이블", "공용 HTTP 유틸")
- 스크립트가 원문의 식별자가 출력에 그대로 나왔는지 검사하고, 나왔으면 기록을 거부한다
