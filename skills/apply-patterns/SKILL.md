# apply-patterns — 지원 패턴 분석

쌓인 지원 기록에서 반복되는 탈락·실패 지점을 찾아 전략 수정안을 만든다.

## 0. 준비

`~/.claude/chwijun-copilot.json`을 읽는다. 없으면 `/chwijun-copilot:wiki-bootstrap` 온보딩을 안내하고 중단한다.

## 1. 원칙

- **탈락 / 지원 실패(미제출) / 지원 전(백로그)을 섞지 않는다.** "계속 떨어진다"는 체감이 실제로는 미제출일 수 있다 — 구분이 분석의 첫 결과물이다.
- **인과 겸손.** 표본이 작으면 "서류 품질이 나쁘다" 같은 단정을 하지 않는다. 타게팅·연차·스택 불일치처럼 확인 가능한 원인부터 소거하고, 남는 것만 가설로 표시한다.
- **최소 표본**: 제출 이후 단계(지원완료·코테 중·서류통과·면접·최종합격·탈락)가 5건 미만이면 §3에서 퍼널과 미제출 손실까지만 하고 멈춘다. 탈락 건 소거법·반복 패턴 명명은 미달을 선언한 뒤에도 하지 않는다 — 미달 고지 후 이어서 분석하는 것이 이 규칙의 주된 위반이다. 미제출(지원 실패·마감 지난 지원 전)은 표본 수에 넣지 않지만, 미제출 자체의 시기 패턴은 표본과 무관하게 보고한다.

## 2. 재료 수집

1. 트래커 전수 조회 (상태·마감일·등록일) — `tracker`가 local이면 `<wiki_path>/지원현황.md`, notion이면 설정의 DB
2. 탈락·지원완료 행의 본문 — job-fit이 남긴 적합도 점수·결정적 갭·제출물 기록
3. `<wiki_path>/프로필.md` — 요구사항 불일치(스택·연차·도메인) 대조 기준
4. `<wiki_path>/문서/`의 면접 회고 문서(있으면) — 어느 단계·어떤 질문에서 막히는지, 승패보다 해상도 높은 신호

## 3. 분석

- **퍼널**: 등록 → 제출 → 서류통과 → 코테 → 면접 → 최종. 단계별 수치와 어디서 새는지
- **미제출 손실**: '지원 실패'·마감 지난 '지원 전' 건수와 시기별 패턴
- **탈락 건 소거법**: 각 탈락마다 스택 불일치 / 연차 미달 / 도메인 무관 / 일괄지원(맞춤 없음) 여부를 본문 기록으로 확인 → 설명되지 않고 남는 탈락만 서류·답변 품질 가설로
- **반복 패턴만 보고**: 2건 이상에서 나타난 것. 1건짜리는 쓰지 않는다
- 탈락 단계(서류/코테/면접) 기록이 없어 분석이 막히면 그 한계를 명시하고, 탈락 단계 기록 추가를 제안한다 (실행은 사용자 확인 후)

## 4. 출력

① 퍼널 수치 표 ② 반복 패턴 (근거 행 명시) ③ 액션 3~5개 (우선순위순, "이번 주에 할 수 있는 것" 우선) ④ 데이터 한계와 다음 분석까지 쌓을 것. 트래커 행 수정은 하지 않는다 — 제안만.
