# 이력서 · 경력기술서 작성 규칙

직군 무관 범용. 이 문서 하나만 있으면 다른 AI 도구에 그대로 붙여 넣고 쓸 수 있다.

---

## 0. 절대 원칙

이 여섯 개를 어기면 아래 규칙을 아무리 잘 지켜도 소용없다.

1. **자랑집이 아니라 사용설명서다.** "내가 이것도 했고 저것도 했다"가 아니라 **"나를 어떤 일에, 어떻게 쓰면 좋은지"** 를 알려주는 문서다. 이 문서를 다 읽은 사람이 "이 사람한테 무슨 일을 맡기면 되겠다"를 한 문장으로 말할 수 있어야 한다.
2. **사실만 쓴다.** 부풀린 한 줄이 문서 전체의 신뢰를 깎는다.
3. **면접에서 5분 설명 못 할 문장은 지운다.** 이력서는 면접 질문지다. 설명할 수 없는 문장은 스스로 판 함정이다.
4. **주어는 항상 "나"다.** 팀이 한 일과 내가 한 일을 분리한다. "우리 팀은 ~했다"는 나에 대해 아무것도 말해주지 않는다. 내 일의 단위는 코드 타이핑이 아니라 **판단**이다 — 문제를 정의하고, 방향을 정하고, 결과를 검증한 것. AI가 코드를 썼어도 그 판단이 내 것이면 내 일이고, 커밋이 내 이름이어도 판단을 안 했으면 내 일이 아니다.
5. **결과만 쓰면 운이고, 결정이 있어야 실력이다.** 무엇을 했는지보다 **왜 그걸 골랐는지**가 사람을 구별한다.
6. **읽는 사람은 30초 안에 넘길지 말지 정한다.** 첫 화면에 승부를 건다.

## 1. 문서 구조

### 1-1. 이력서 (1~2장)

```
1. 인적사항        이름 / 연락처 / 이메일 / GitHub·포트폴리오 링크
2. 헤드라인        나를 한 문장으로 정의
3. 요약(Summary)   태그 블록 2개
4. 경력 · 프로젝트  최신순
5. 기술 스택
6. 학력 · 교육 · 자격
7. 기타            수상 / 발표 / 오픈소스 / 글
```

사진·주소·나이·성별은 공고가 요구할 때만 넣는다.
경력이 짧으면 4번을 줄이는 대신 프로젝트·활동·교육의 **밀도**로 채운다. 칸을 비워두는 것보다 낫다.

**헤드라인 + 요약 패턴** (실제 합격 이력서에서 검증된 형태)

```
[Flutter와 iOS를 아우르는 모바일 개발자]
- 스타트업에서 앱 개발 전담, 설계부터 스토어 출시·운영까지 전 과정 주도
- GitHub Actions 기반 CI/CD 구축
- App Store 라이프스타일 카테고리 50위 달성

[협업과 지식 공유에 열정적인 개발자]
- 기획자, 백엔드·AI·웹 개발자와 협업하며 제품 개발
- GDSC 모바일 세션 리드
- 연합 해커톤 2등 등 팀 프로젝트 수상
```

- 태그는 **2개까지**. 3개가 넘으면 "다 잘한다 = 뭘 잘하는지 모르겠다"가 된다.
- 두 번째 태그는 첫 번째와 다른 축을 잡는다. 기술축 하나 + 협업/성장/도메인 축 하나.
- 각 태그 아래 근거 불릿 3~5개. 근거 없는 태그는 자기 주장일 뿐이다.

### 1-2. 경력기술서 — 프로젝트당 고정 템플릿

```
프로젝트명                                        2024.01 ~ 2024.07

[서비스 설명]  이 기능/서비스가 무엇인지, 처음 보는 사람 기준으로 1~2문장. 필수 슬롯 — 비우면 아래가 전부 안 읽힌다.
[맥락]  왜 이 일이 생겼는지
[기술]  사용 기술 한 줄 나열
[역할]  팀 규모 / 내 포지션 / 담당 범위 한 줄
[한 일] 불릿 4~8개
```

**기간 옆에 총 기간을 괄호로 단다** — `2024.01 ~ 2024.07 (7개월)`. 심사자가 프로젝트 규모를 한눈에 잡는다. 단, 모르는 기간을 그럴듯하게 지어내지 않는다(§0.2) — 실제 기간만, 모르면 월 단위까지만 쓴다.

**서비스 설명을 먼저 주는 게 핵심이다.** 읽는 사람은 그 서비스를 모른다.
"CRM 백오피스 개발"만 보면 아무 그림도 안 그려지지만, "리뉴얼될 CRM 서비스의 사용자·캠페인·로그를 사내에서 관리하기 위한 백오피스"라고 한 줄 깔아주면 이후 불릿이 전부 읽힌다.

**사내 용어 금지.** 기능명·시스템명·조직 약어·도메인 은어는 그 회사 사람만 안다. 인사담당자는 모르는 단어를 만나면 추측하다가 넘긴다 — "그래서 뭘 했다고?"로 끝난다.

> ❌ 학습자가 미션을 끝내면 동료에게 평가를 요청하고 시간 슬롯을 잡습니다 (미션? 시간 슬롯? 평가 요청?)
> ✅ 학습자들이 서로의 과제를 평가하고 그 대가로 포인트 — 플랫폼 안에서 화폐처럼 도는 재화 — 를 주고받는 기능입니다

판별법: **그 단어를 회사 밖 친구가 알아듣는가.** 아니면 ① 보편 용어로 바꾸거나 ② 반 줄로 정의하고 쓴다. 지원 직군의 언어로 번역하면 더 좋다 (포인트 반환 버그 → "환불 이중 처리와 같은 결함").

**한 문단 안에서 독자를 층으로 나눈다.** 서류는 두 명이 읽는다 — 비개발 스크리너, 그다음 개발 면접관.

```
앞부분 (무슨 서비스 · 무슨 문제)   비개발자도 따라오게. 긴 설명이 아니라 비유 앵커 한 구절이 일한다
                                  — "환불이 두 번 처리되는 것과 같은 결함", "화폐처럼 도는 재화"
뒷부분 (어떻게 풀었나)             기술 용어 그대로. 조건부 UPDATE, affected rows — 개발 면접관 몫이다.
                                  비개발자용으로 순화하면 오히려 기술 검증에서 무너진다
```

검증 근거: 동일 문단 A/B 페르소나 테스트에서 용어 나열형은 "기능이 뭔지 모르겠다"(5/10, 스킵), 비유+층위형은 "비개발자인 나도 따라갔다, 서류 통과"(6/10). 비개발자는 뒷부분을 어차피 안 읽는다 — 앞부분만 통과시키면 된다.

정렬은 **최신순**. 오래된 걸 위에 올리면 지금 뭘 할 수 있는 사람인지 파악하는 데 시간이 걸린다.

### 1-3. 트러블슈팅 — 반드시 별도 섹션으로

합격 문서들의 가장 뚜렷한 공통점이다. 프로젝트 불릿에 섞지 말고 독립 섹션으로 뺀다.

```
### 문제를 한눈에 보여주는 제목

상황:   무엇이 왜 문제였나
시도 1: 무엇을 했고 왜 안 됐나
시도 2: 무엇을 했고 왜 안 됐나
해결:   최종적으로 무엇을 했나
배운 것: 다음에 비슷한 상황에서 뭘 다르게 할 건가
```

**실패한 시도를 반드시 쓴다.** 이게 이 섹션의 전부다.
한 번에 딱 해결한 이야기는 검증이 안 되고, 무엇보다 지어낸 티가 난다. 막다른 길이 있어야 실제로 겪은 일로 읽힌다.

> 예: WYSIWYG 에디터가 필요했다. react-quill로 만들었는데 Chrome에서 deprecated 예정인 이벤트를 쓰고 있었고, 릴리스 이력상 고쳐질 기미가 없었다. sun-editor로 갈아탔더니 이번엔 사용성 이슈가 걸렸다. 이슈 트래커를 뒤져보니 역시 개선 계획이 없었다. 두 번 엎고 나서, 쓰기는 까다롭지만 가장 활발히 관리되는 Lexical을 골랐다. 라이브러리를 고를 때 기능보다 유지보수 상태를 먼저 본다.

3~6개면 충분하다. 서로 다른 종류의 문제를 고른다 — 성능 하나, 설계 판단 하나, 협업/프로세스 하나, 처음 써보는 기술 하나.

**개선 후 수치를 못 잰 건**은 「배운 것」이 결과를 대신한다. 감상이 아니라 규칙 문장으로 쓰는 법 → `references/portfolio.md` §5

## 2. 성과 서술 공식

**문제 → 선택 → 결과 → 근거**, 네 칸을 채운다.

### 서술형 (경력기술서 · 트러블슈팅)

> ❌ REST API를 개발하여 서비스 안정성을 향상시켰습니다.

문제 없음, 선택 없음, 숫자 없음. 아무나 쓸 수 있는 문장이고 그래서 아무 정보도 없다.

> ✅ 주문 조회 API가 피크 시간대에 3초를 넘겨 타임아웃이 났다. 인덱스를 손봤지만 조인 자체가 병목이라 한계가 있었고, 조회 전용 테이블을 따로 두는 쪽을 택했다. 쓰기 지연은 감수했다. p99가 3.1초에서 240ms로 떨어졌다.

### 압축형 (이력서 불릿) — 콜론 앞에 결과, 뒤에 방법

```
주문 조회 p99 3.1초 → 240ms: 인덱스 튜닝 한계 확인 후 조회 전용 테이블 분리
Flutter Web 초기 로딩 60% 단축: CanvasKit 번들 최적화
셀 재사용 데이터 꼬임 해결: prepareForReuse 활용
```

가장 먼저 읽히는 자리에 가장 강한 정보를 둔다. 방법은 그 뒤에 붙는다.
불릿 하나가 3줄을 넘으면 쪼개거나 트러블슈팅 섹션으로 옮긴다.

### "선택" 칸을 가설 형태로

네 칸 중 가장 자주 비는 게 **선택**이다. 그냥 적으면 결정이 아니라 사실 기록이 된다.
가설 형태로 쓰면 사고 과정이 드러난다.

```
가설: X를 하면 Y가 개선될 것이다. 근거는 Z다.
검증: 어떻게 확인했나
결과: 맞았나, 틀렸나
```

"~일 것 같아서 해봤다"는 가설이 아니다. 근거(Z)가 있어야 가설이다.
그리고 **가설이 틀렸던 사례가 더 좋은 소재다.** 맞은 이야기는 결과 자랑에서 끝나지만, 틀린 이야기는 언제 알아챘고 무엇으로 갈아탔는지까지 보여준다.

포트폴리오처럼 길게 서술하는 문서에서는 이 칸을 독립 항목으로 뺀다 → `references/portfolio.md`

### 연차 프레임 — 3년차부터 "직접 개선"이 주어다

3~5년차는 주니어→미들 경계다. "배웠다·성장했다" 프레임은 주니어로 읽히게 만든다.
주어를 **내가 직접 개선한 기능·코드·프로세스 + 수치**로 잡아야 미들로 읽힌다.
배운 점은 트러블슈팅의 「배운 것」 칸에서만, 규칙 문장으로 쓴다.

## 3. 수치화

성과를 수치로 정량화한 이력서는 합격률이 13% 높았다(원티드 실측 데이터). 감이 아니라 측정된 차이다.

### 숫자로 바꿀 수 있는 것

| 범주 | 예시 |
|---|---|
| 성능 | 응답 시간(p50/p99), 처리량, 빌드·배포 시간, 메모리, 쿼리 수 |
| 규모 | DAU/MAU, 요청 수, 데이터 건수, API·화면·컴포넌트 개수 |
| 시간 | 개발 기간, 자동화로 없앤 수작업 시간, 온보딩 시간 |
| 품질 | 장애 건수, 버그 리포트, 테스트 커버리지, 롤백 횟수 |
| 팀 | 인원, 리뷰한 PR 수, 작성한 문서·가이드 |
| 비즈니스 | 매출, 전환율, 스토어 순위, 다운로드, 이탈률 |

### 숫자가 없을 때 — 세 가지 대안

1. **개수로 대체** — "UI 컴포넌트 약 45종 개발", "주요 화면 15개 구현"
2. **비교로 대체** — "배포 수작업 3단계 → 1단계 자동화", "Vue 페이지 8개를 React로 이관"
3. **검증 방법을 대신 쓴다** — "k6로 동시 500 부하 테스트하여 확인"

셋 다 안 되면 숫자를 만들지 말고 **결정의 근거**를 쓴다. 근거 있는 서술은 가짜 숫자보다 강하다.

업계가 실제로 쓰는 지표 체계(DORA 4 Keys · SLI/SLO · SPACE)와 백엔드 지표 목록은 → `references/kpi.md`

### 부풀리기 경계선

| 하지 말 것 | 대신 |
|---|---|
| 팀 성과를 내 성과처럼 | "3인 팀에서 결제 모듈 담당. 서비스 전체는 …" — 기여 범위를 먼저 밝히고 팀 성과를 언급 |
| 추정치를 측정치처럼 | "체감상 빨라짐"이면 측정하지 않았다고 쓰거나 빼기 |
| "최초 / 유일 / 혁신 / 획기적" | 사실이어도 안 쓴다. 검증 요구만 부른다 |
| 기준 없는 퍼센트 | "효율 30% 개선" → 무엇을 어떻게 쟀는지 못 쓰면 삭제 |

## 4. 기술 스택

**나열은 정보가 아니다.**

> ❌ IOS Swift Flutter Git GitHub Slack RxSwift API RestAPI MVVM Clean Architecture Observer Pattern riverpod provider Singleton Pattern Cubit Dart 앱개발 Firebase Supabase Objective-C Node.js React SDK GraphQL 유지보수 기술지원 트러블슈팅 디자인 JavaScript ReactJS MyBatis MongoDB

40개를 늘어놓으면 읽는 사람은 "이 중에 진짜 뭘 할 줄 아는지" 판단할 방법이 없다. 주력 기술까지 같이 희석된다. `Git`, `Slack`, `유지보수`, `디자인` 같은 항목은 아무것도 구별해주지 못하므로 그냥 뺀다.

### 방법 A — 3단 분류

```
주력     면접에서 깊게 파고들어도 되는 것.        3~5개
사용     실무에 바로 투입 가능한 것.             5~8개
경험     써봤지만 얕은 것. 필요할 때만 적는다.
```

### 방법 B — 기술별 한 문장 (권장)

```
TypeScript  인터페이스와 제네릭을 활용해 타입 단위로 오류를 사전에 걸러낼 수 있습니다.
Next.js     SSR의 초기 로딩·SEO 이점을 이해하고 서버/클라이언트 컴포넌트를 구분해 씁니다.
```

무엇을 할 수 있는지 한 줄씩 쓰면 그 자체가 **면접 예상 질문표**가 된다. 자기가 못 쓸 문장은 애초에 못 적으므로 자동으로 정직해진다.

### 금지

별점 · 퍼센트 · 막대그래프 · 상중하 숙련도 표기. 기준이 없어 정보를 주지 못하고, 낮게 매긴 항목은 스스로 만든 감점 요인이 된다. 채용 플랫폼의 스킬 등록란(원티드 등)은 4개 내외가 합격률이 가장 높았다(원티드 데이터) — 등록란은 주력만, 나머지 JD 키워드는 경력기술서 본문에 녹인다.

---

## 5. 문장 규칙 — AI 티 제거

상세 내용과 프롬프트는 `references/ai-detection.md`. 핵심만 옮기면:

1. **문장 길이를 섞는다.** 짧은 문장과 긴 문장을 교차시켜 리듬을 만든다. 비슷한 길이가 이어지면 기계로 찍어낸 티가 난다.
2. **같은 구조를 3번 이상 반복하지 않는다.** "~하여 ~했습니다"가 연달아 세 번 나오면 하나는 어순을 바꾼다.
3. **어순을 흔든다.** 결과를 앞으로 빼거나, 목적어를 문두로 올리거나, 조건절 위치를 바꾼다.
4. **실무 용어를 쓴다.** 현장에서 실제로 쓰는 단어가 들어가면 겪어본 사람의 글이 된다.
5. **종결어미는 통일하되 문장 구조는 통일하지 않는다.** 개조식('~했다')이든 경어체('~했습니다')든 문서 안에서는 하나로. 구조까지 똑같아지면 안 된다.

## 6. 금지 목록

### 6-1. 상투적 접속사 — 전부 삭제

```
또한  ·  결론적으로  ·  결과적으로  ·  뿐만 아니라  ·  나아가
이를 통해  ·  따라서  ·  이러한  ·  마지막으로
```

접속사를 지우면 대부분 문장이 더 좋아진다. 연결이 정말 필요하면 문장을 끊어 두 문장으로 만든다.

### 6-2. AI 상투 표현

- 대상 없는 추상 명사 — 성장 / 기여 / 역량 강화 / 시너지 / 최적화 / 고도화
- 거창한 한자어 동사 — "체득했습니다" / "내재화했습니다" / "고도화했습니다" → 배웠습니다 / 익혔습니다 / 개선했습니다. 연차보다 큰 동사는 부풀림으로 읽힌다 (단, 평이한 동사로 바꿔도 6-2의 감정·소감 문장이 되면 삭제 대상)
- "~에 대한 이해를 바탕으로", "~을 통해 ~할 수 있었습니다", "~에 힘썼습니다"
- 태도 부사 — 적극적으로 / 능동적으로 / 끊임없이 / 열정적으로 / 주도적으로
- 텅 빈 수식 — 다양한 경험 / 폭넓은 이해 / 깊이 있는 고민 / 탄탄한 기본기
- 3연속 명사 나열 — "확장성, 유연성, 안정성을 고려하여"
- 감정·소감 문장 — "많은 것을 배웠습니다" / "값진 경험이었습니다" / "책임감을 느꼈습니다" / "최선을 다했습니다" / "자신감을 얻었습니다". 배운 게 있으면 **다음에 무엇을 다르게 하는지**로 쓴다

> 판별법: 문장에서 회사명과 기술명을 지웠을 때 **다른 지원자의 이력서에 그대로 붙여도 말이 되면** 그 문장은 삭제 대상이다.

### 6-3. 형식에서 나는 냄새

- 굵은 글씨 남발 (강조가 많으면 강조가 없는 것과 같다)
- 이모지 (섹션 헤더 아이콘 1~2개까지는 허용)
- 모든 불릿의 길이가 균일한 것 — 사람이 쓰면 길이가 들쭉날쭉하다
- 모든 섹션의 불릿 개수가 똑같이 3개 또는 5개

## 7. 분량 · 포맷

| 항목 | 기준 |
|---|---|
| 이력서 | 신입 1장 / 3년 이하 1~2장 / 그 이상 2장 |
| 경력기술서 | 프로젝트당 1페이지 이내 |
| 프로젝트 수 | 깊게 쓰는 건 3~4개까지. 나머지는 1줄 압축 (1~3년차 기준 · 5년차 이상도 최대 10개) |
| 합산 상한 | 이력서 + 경력기술서 4장 이내 (원티드 합격 이력서 평균 2.7장) |
| 불릿 | 1~2줄. 3줄 넘으면 쪼갠다 |
| 파일 | PDF 제출이 기본. 노션 포트폴리오는 단독 제출하지 말고 링크로 병기 (링크 차단 회사 존재) |

- **링크는 제출 직전에 전부 눌러본다.** 깨진 링크 하나가 성의 없음의 증거가 된다.
- GitHub는 README가 정리된 저장소만 건다. 커밋 3개짜리 실습 저장소가 최상단에 있으면 안 거는 게 낫다.
- **마이너스 요소는 선제 해명한다.** 공백기, 짧은 재직, 잦은 이직은 숨기면 더 크게 걸린다. 사실만 담백하게 한 줄. 변명은 붙이지 않는다.
  > `※ 회사 경영악화로 인한 사업 종료에 따른 퇴사`

## 8. 제출 전 체크리스트

문서 전체를 훑으며 항목별로 통과/실패를 판정한다. "괜찮아 보인다"는 판정이 아니다.

**내용**
- [ ] 모든 문장이 사실이고, 각각을 5분간 설명할 수 있다
- [ ] 팀 성과와 내 기여가 구분되어 있다
- [ ] 프로젝트마다 서비스 설명(이게 뭔지)과 맥락(왜)이 먼저 나온다
- [ ] **회사 내부인만 아는 용어가 0개다** — 기능명·시스템명·조직 약어를 회사 밖 친구 기준으로 스캔
- [ ] 주요 성과마다 숫자 또는 대체 근거가 있다
- [ ] "왜 그 방법을 골랐는지"가 최소 3곳에 드러난다
- [ ] 트러블슈팅 섹션에 **실패한 시도**가 적혀 있다

**문장**
- [ ] 6-1 금지 접속사가 0회
- [ ] 6-2 상투 표현이 0회
- [ ] 회사명·기술명을 지웠을 때 아무 데나 붙일 수 있는 문장이 없다
- [ ] 같은 문장 구조가 3연속으로 나오지 않는다
- [ ] 문장 길이가 들쭉날쭉하다

**형식**
- [ ] 분량이 기준 안에 있다 (이력서+경력기술서 합산 4장 이내)
- [ ] 모든 링크가 열린다
- [ ] 종결어미가 문서 전체에서 통일되어 있다
- [ ] 날짜 표기 형식이 통일되어 있다 + 총 기간 표기 (`2024.01 ~ 2024.07 (7개월)`)
- [ ] 공백기·이직 사유 등 예상되는 의문에 선제 답변이 있다

**읽는 사람 관점** — 문서를 덮고, 처음 보는 사람이 되어 네 질문에 답해본다

- [ ] 이 사람을 뽑으면 **어떤 일을 맡길 수 있을까** → 한 문장으로 나오나
- [ ] **스스로 문제를 찾아 움직이는 사람인가, 시키는 일만 하는 사람인가** → 스스로 정의한 문제가 최소 1개 있나
- [ ] 실수해도 **빨리 배우고 성장할 사람인가** → 실패와 그 이후가 적혀 있나
- [ ] **지금 이 팀에 없는 무엇을 가져오는가** → 다른 지원자와 구별되는 지점이 있나

넷 중 하나라도 "이 문서로는 모르겠다"가 나오면 그 항목을 채우러 돌아간다.

**마무리**
- [ ] 소리 내어 한 번 읽었다 — 입에 안 붙는 문장은 남의 문장이다
- [ ] 이 문서로 예상 질문 10개를 뽑아 답변을 준비했다 (`references/interview-prep.md`)
