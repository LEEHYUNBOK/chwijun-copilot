# 이력서 작성

이력서·경력기술서·자기소개서를 쓰고 고치는 작업의 진입점.
규칙 본문은 이 파일에 없다. 아래에서 해당 작업을 고르고, 명시된 파일을 **읽은 다음** 작업한다.

경로 규약: 이 스킬의 베이스 디렉터리 기준 두 단계 위가 플러그인 루트다. 스크립트는 `<스킬 베이스 디렉터리>/../../scripts/`에 있다.

## 작업 라우팅

| 요청 | 읽을 파일 |
|---|---|
| 이력서·경력기술서 작성/수정/검토 | `rule.md` |
| 포트폴리오 (프로젝트 상세 서술) | `rule.md` + `references/portfolio.md` |
| 자기소개서 (문항형) | `rule.md` + `references/cover-letter.md` + `references/ai-detection.md` (자소서는 산문이라 문체가 그대로 드러난다 — 인간화를 나중에 붙이지 말고 처음부터 읽는다) |
| 특정 공고에 맞춰 커스터마이징 | `rule.md` + `references/jd-tailoring.md` |
| 공기업·공공기관 (NCS·블라인드) | `rule.md` + 추가 규칙: 경험을 STAR(상황-과제-행동-결과)로 정리하되 행동(Action) 비중 최대, 판단 기준·선택 이유가 드러나게. NCS 직업기초능력 중 부합 항목 1개+ 매칭. 학벌·나이·출신 언급 배제 |
| 면접 대비 / 예상 질문 뽑기 | `references/interview-prep.md` |
| "AI 티 난다" / 문체 다듬기 | `references/ai-detection.md` |
| 최신 트렌드·실제 예시·서류 평가 기준 | `references/field-guide-2026.md` (웹 16개 소스, rule.md 보강) |

어떤 작업이든 `rule.md`의 **0장(절대 원칙)** 과 **8장(체크리스트)** 은 항상 적용된다.

## 공통 워크플로우

### 1. 재료부터 확보한다 — 빈칸 채우기 금지

사용자의 실제 경험을 모르는 상태에서 문장을 지어내지 않는다. 없으면 묻는다.
필요한 재료:

- 지원 대상 (회사 / 직무 / 공고 원문)
- 기존 이력서·경력기술서 (있으면 반드시 먼저 읽는다). 없으면 경력 위키의 `<wiki_path>/프로필.md`와 `문서/`가 1차 재료다 (`~/.claude/chwijun-copilot.json`의 wiki_path)
- 각 프로젝트의 **문제 상황**, **그때 세운 가설과 근거**, **내가 내린 결정**, **결과 숫자**

셋 중 하나라도 비어 있으면 그 항목에 대해 질문한다. 한 번에 하나씩.
숫자를 모른다고 하면 지어내지 말고 `rule.md` 3장의 대체 전략을 쓴다.
초안 단계에서 확인 못 한 정보는 채워 넣지 말고 본문에 `[추가 확인 필요: 무엇]`으로 표시해 남긴다 — 사용자가 한눈에 뭘 채워야 하는지 보인다.

### 1-1. 기여도 판정 — 커밋 작성자 기준 금지

AI가 코드를 쓰는 시대다. 코드 저자(커밋 작성자·git blame)는 기여도의 근거가 아니다.
서술의 축은 세 가지다 — **어떻게 기획했는가 · 어떻게 고도화했는가 · 어떻게 성능을 향상시켰는가.**

- 코드·repo 분석은 "무엇이 어떤 구조로 설계·개선되었나"를 추출하는 용도로만 쓴다. 작성자 판정에 쓰지 않는다.
- 확정된 참여도에도 `rule.md` 0장 3번은 그대로 적용된다 — 면접에서 5분 설명 못 할 문장은 못 쓴다. 이게 git blame을 대신하는 진짜 안전장치다.

### 2. 초안은 사용자 문장을 살려서 쓴다

사용자가 이미 쓴 표현이 있으면 그 어휘와 리듬을 유지한 채 구조만 고친다.
완전히 새 문장으로 갈아엎으면 (a) 본인 목소리가 사라지고 (b) 면접에서 자기 이력서를 설명하지 못하게 된다.

### 3. 고칠 때는 이유를 붙인다

`이 문장 → 저 문장` 만 던지지 말고, 어떤 규칙 때문에 고쳤는지 한 줄로 밝힌다.
사용자가 규칙을 익혀야 다음부터 혼자 쓸 수 있다.

### 4. 검토는 체크리스트로 한다

작성이 끝나면 `rule.md` 8장 체크리스트를 항목별로 통과/실패 판정한다.
"좋아 보입니다" 같은 총평은 쓸모없다. 실패한 항목과 위치를 지목한다.

**기계 검사부터 돌린다 (토큰 절약).** 접속사·감정문장·연결어미 쉼표·금지어를 결정적으로 잡는 스크립트가 플러그인에 있다 — LLM으로 스캔하지 말고 이걸 실행한다:

```bash
python3 "<스킬 베이스 디렉터리>/../../scripts/check_voice.py" --banned <본인 금지어 파일> <파일>...
```

금지어 파일은 플러그인의 `scripts/금지어-공통.txt`를 `<wiki_path>/`에 복사해 본인 회사의 내부 용어·대외비 식별자를 채워서 쓴다.
스크립트가 잡는 것은 스크립트에 맡기고, LLM 검토는 판단이 필요한 것(사실성·맥락·설득력)에만 쓴다.

## 배열·수치 원칙

- **소재 배열은 JD 적합도 순. 위에서부터 읽다 만다.** 이력서·자소서·역량기술서 어디든, 소재를 시간순·작업 규모순·쓰기 편한 순으로 늘어놓지 않는다. **공고 직무명과 담당업무에 가장 가까운 것이 1번**이고 나머지가 그 아래다.
  - 판별법: 공고 직무명을 소리 내어 읽고, 1번 소재가 그 직무명의 **첫 단어**에 답하고 있는지 본다. "플랫폼 개발/운영" → 1번은 개발 소재
  - 역량기술서·경력기술서의 **섹션 순서에도 그대로 적용**한다. 섹션 제목만 JD순이고 내용이 안 맞으면 소용없다
  - JD 원문이 없으면 직무명만으로 배열하되 **그 가정을 명시**하고 넘긴다. 추측한 순서를 말없이 확정하지 않는다
- **수치는 결과 KPI만.** 커밋 수·라인 수·소요일 같은 노력량 수치 금지. before→after 형태로 쓴다 (`references/kpi.md`)

## 하지 말 것

- **경험 창작.** 사용자가 말하지 않은 프로젝트, 하지 않은 기술, 측정하지 않은 숫자를 만들어내지 않는다. 이건 그냥 거짓말이고, 면접 5분 안에 들통난다.
- **한 번에 전부 쓰기.** 섹션 단위로 쓰고 확인받는다.
- **AI 검사기 통과 자체를 목표로 삼기.** `references/ai-detection.md`의 프레이밍을 따른다 — 목표는 진짜 본인 경험을 본인 목소리로 쓰는 것이고, 검사기 통과는 그 부산물이다.
