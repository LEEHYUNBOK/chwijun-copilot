# 국내 개발자 이력서·경력기술서 실전 가이드

수집된 16개 소스(채용 플랫폼, 현직자 블로그, 커뮤니티 Q&A, 강의)를 교차 정리했다. 여러 소스가 반복해서 말하는 것일수록 신뢰도가 높다.

## 1) 핵심 원칙 — 여러 소스가 공통으로 말하는 것

가장 많은 소스가 겹치는 순으로 정렬했다.

**① 기술 스택 나열이 아니라 "문제 → 해결 → 결과 변화"의 서사로 쓴다** (거의 모든 소스)
- "무엇을 했다"가 아니라 "어떤 문제가 있었고, 왜 그 방식을 택했고, 결과가 어떻게 달라졌는지"를 보여야 한다.
- 근거: 서치라이트 경력기술서 예시(2026) / 잡코리아 / 프로그래머스 이력서 클리닉 / 인프런 / 우아한형제들 / velog @sammy1 STAR

**② 성과는 반드시 정량화한다 (Before→After 수치)** (거의 모든 소스)
- 예: 응답 1.8초→420ms, 페이지 로딩 1.2초→0.7초, 결제 실패율 0.8%→0.2%, 조회 속도 65% 단축, Lighthouse 58→86.
- "긍정적 평가를 받았습니다"(탈락) vs "팔로워 200% 증대(1.2만→3.6만)"(합격).
- 근거: 서치라이트(양 소스) / 잡코리아 / 링커리어 / velog @sammy1(양 소스) / 이랜서

**③ STAR / PAAR 구조가 표준 골격이다** (다수 소스)
- STAR: 상황-과제-행동-결과. 변형 PAAR: Problem-Analyze(대안 검토)-Action-Result.
- Action(행동)이 서술의 50% 이상을 차지하되, 면접관은 Analyze(왜 그 기술을 골랐는가)를 더 중시한다.
- 근거: 서치라이트 / 링커리어 / velog @sammy1 STAR / 잡코리아

**④ JD 적합성 우선 — 관련 경험을 상단에, 프로젝트는 3~5개로 압축** (다수 소스)
- 지원 포지션과 무관한 경험은 삭제하거나 1줄로 압축. 기본 이력서 하나를 두고 공고별로 강조 프로젝트·키워드 순서만 조정.
- 근거: 서치라이트 개발자 경력기술서(2026) / 프로그래머스 / OKKY 3년차 / 인프런 / 잡코리아

**⑤ 1인칭("내가")으로, 형용사·수동형을 지운다** (다수 소스)
- "우리"를 "나"로, "열정적·성실한·참여했습니다"를 구체적 행동·수치로 교체.
- 근거: velog @sammy1(양 소스) / 서치라이트 / Wonny Log

**⑥ 제출은 PDF + 포트폴리오 링크(노션/깃허브)** (다수 소스)
- 이력서(핵심 요약) 1페이지 + 포트폴리오(프로젝트 상세)를 별도 문서로. HWP/워드 금지. 파일명은 `이름_직무_날짜.pdf`.
- 근거: 링커리어 / DoDo / Wonny Log / velog @sammy1 탈락7가지

## 2) 구조·형식 — 이력서 / 경력기술서 구성

**문서 역할 분리** (velog @jhbae0420 / OKKY 3년차 / DoDo)
- **이력서**: 핵심 성과를 빠르게 보여주는 요약 문서.
- **경력기술서**: 프로젝트별 역할·기술 스택·기여도를 상세히 설명.
- **자기소개서**: 위 둘과 다른 역할. 세 문서를 비슷하게 쓰는 것이 흔한 실수.

**이력서 5대 구성** (링커리어)
1. 개인정보 + 한 줄 소개
2. 기술 스택
3. 프로젝트 경험
4. 경력·인턴
5. 교육·자격증·기타

**분량**
- 이력서 1페이지 기본 (링커리어 / DoDo / Wonny Log).
- 경력직 이력서는 A4 2~3장, 핵심 프로젝트 3~4개 (잡코리아 / OKKY 3년차).
- 프로젝트 수: 1~3년차 3개 내외, 5년차 5개 안팎(최대 10개 이내). 완성도 우선 (서치라이트 / 이랜서 / 링커리어).

**기술 스택 작성**
- 주력 6~12개만 선별. 20개 나열은 신뢰도 하락 (velog @sammy1 / 링커리어).
- 각 기술을 "해결한 문제"와 연결. 도구명만 적지 말 것 (프로그래머스 / 인프런 / 서치라이트).
- 숙련도·사용 기간 표기: **의견 갈림** → 5)번 참고.

**시각·서식** (우아한형제들)
- 주소·성별 등 불필요 항목 제거. 학점 생략(Wonny Log).
- 표·줄 빽빽한 고전 양식 대신 여백 있는 레이아웃. 폰트는 애플SD고딕/KoPub돋움 권장(굴림·맑은고딕 지양), 색상 2~3가지로 제한.

**GitHub/포트폴리오 배치** (프로그래머스 / 잡코리아 / 인프런)
- 이력서 상단에 GitHub 프로필 URL, 강조 프로젝트는 해당 레포 URL을 경력 섹션에 함께.
- 레포는 적게 두되 완성도 있게. README에 문제 정의·기술 선택·본인 기여 명시. 미완성 레포는 비공개.

## 3) 성과 서술법 — 프로젝트/성과 쓰는 구체적 방법

**기본 문장 구조** (잡코리아)
> 문제 상황 → 본인 역할(직접 구현 여부) → 해결 방식(선택한 기술·구조) → 결과 변화

예:
- (약함) "코드리뷰를 담당했습니다."
- (강함) "배포 전 리뷰에서 N+1 쿼리 패턴을 발견해 트래픽 특성에 맞게 DB 호출 구조를 개선함."

**STAR 4단계** (velog @sammy1 STAR)
- **S**: 구체적 문제 + 수치. "배포 후 사용자 이탈률 12%까지 증가."
- **T**: 본인 역할 + 명확한 목표. "1주일 내 응답 1초 이내."
- **A**: 전체의 50% 이상. 1인칭으로 도구·방법·기간 구체화.
- **R**: Before→After 비교 필수. "2.5초 → 0.4초 (-84%)."
- 최소 3개의 수치. STAR는 문제 해결 경험에만, 단순 학습·참여는 간단히.

**PAAR 구조 (백엔드 특히 권장)** (서치라이트)
- Problem(왜 중요했나) → Analyze(선택지 검토와 선정 이유) → Action(실행) → Result(변화).
- 면접관은 Action보다 Analyze를 본다.

**직무별 강조점**
| 직무 | 강조 | 지표 예시 |
|---|---|---|
| 백엔드 | 서버구조·API·DB, 병목 파악, 성능·아키텍처 | 응답속도, 오류율, 처리시간, 장애 0건 |
| 프론트엔드 | UI/UX·컴포넌트·상태관리 | 로드타임, Lighthouse, 번들 사이즈 |
| 데이터 | 문제정의·인사이트 | — |
| 풀스택 | 넓이 아님. 업무흐름 개선·부서간 소통비용 절감 | 구조적 효율성 |

근거: 링커리어 / 서치라이트

**백엔드 성과 서술 예시** (이랜서 / 서치라이트)
- "Redis 분산 락으로 중복 알림 방지, AWS SQS 기반 비동기 결제 대기열 설계, 슬로우 쿼리 튜닝·인덱스 최적화 → 어드민 조회 속도 65% 단축."
- 실행 - 결과 - 성과 순서로.

**연차별 무게중심** (잡코리아 / 서치라이트 / DoDo)
- **인턴**: 배운 점·잠재력 중심.
- **신입**: 기술 깊이·수치 성과·문제해결 능력. 토이 프로젝트·대외활동·수업도 무방(인프런). "빠른 러닝커브 + 1인분 잠재력"을 근거와 함께.
- **3~5년차**: 직접 개선한 기능·코드·프로세스 + 전후 변화.
- **6~8년차**: 기술 선택 이유 + 협업 범위. 예 — Kafka/Redis Stream/배치를 비교 평가 후 파티션 순서·재처리·모니터링 기준으로 Kafka 선택. 러닝커브만 앞세우면 안 됨.

**수치화가 어려운 성과** (잡코리아 / velog @sammy1)
- 표준화·기준 정립·재발 방지·리뷰 품질 편차 감소 같은 프로세스 개선 결과로 표현. 문제맥락→역할→해결→관찰 가능한 변화 구조.

**프로젝트 서술 3관점** (우아한형제들)
- 기술적 리더십(어떤 결정) / 프로젝트 관리(역할) / 팀 협업(소통 방식).
- 문제 해결은 "문제정의→원인분석→측정→해결책→실행→평가→회고".

**서비스 소개가 아니라 본인 기여를 써라** (인프런)
- (약함) "신규 강의 플랫폼 서비스 개발"
- (강함) "stub을 이용한 WebClient 테스트 공통 라이브러리 개발"

## 4) 흔한 실수 / 탈락 이유

채용 담당자는 이력서를 **7~30초** 안에 훑는다 (velog @sammy1: 7초 / 서치라이트: 30초).

**내용의 추상성**
- 형용사·수동형만 있고 수치 없음. "참여했습니다"로 끝나는 프로젝트. (velog @sammy1 / 서치라이트)
- 수행 업무만 나열하고 "결과적으로 무엇이 달라졌는지" 없음. (서치라이트 / 잡코리아)
- 경력에 기간·회사명·타이틀만 있고 상세 업무 없음 → 의사소통 능력 의심 (OKKY 서류탈락).
- 자기소개서가 뻔하고 이력을 너무 길게 나열 → 식상 (OKKY 서류탈락).
- 신입: 이력서에서 자신을 충분히 설명 못 함(설명 부족)이 주요 탈락 원인 (velog @jhbae0420).

**형식·성의 문제**
- 기술 스택 20개 나열 (velog @sammy1).
- HWP/워드 제출 (PDF 아님) (velog @sammy1 / Wonny Log).
- 권한 막힌 노션 링크, 404이거나 빈 GitHub, README 없는 레포 (velog @sammy1 / 잡코리아).
- 파일명 "이력서.pdf" (velog @sammy1).
- 완성도 낮은 사이드 프로젝트 나열, 이전 회사명·고객사명·개인정보 노출 (잡코리아).

**기타 오판 포인트**
- 자격증 개수는 평가 포인트가 아님 — 실질 개발 역량이 우선 (OKKY 서류탈락).
- 채용공고 기술 스택 그대로 나열 (서치라이트).
- 없던 것을 만들거나 과장 → 면접에서 드러남 (우아한형제들 / Wonny Log).
- 이력서·경력기술서·자소서를 비슷하게 씀 (velog @jhbae0420).

## 5) 의견이 갈리는 지점

**① 기술 스택 숙련도 표기 여부** — 상충
- **표기하라**: "숙련도(기초/중/상)와 사용 목적을 함께 적으면 신뢰도 상승" (링커리어). 인프런도 "얼마나 오래·어느 수준으로 다루는지" 서술 권장.
- **표기하지 마라**: "숙련도 표시는 불필요, 경험에서 드러나야 한다" (Wonny Log).
- 판단: 신입/주니어는 목적·기간 정도만 간단히, 경력은 프로젝트 서술로 대체하는 절충이 무난. (편집자 의견)

**② 서류 최적화 자체의 유효성** — 트랙에 따라 다름
- 대부분 소스는 서류가 1차 관문임을 전제.
- 그러나 토스처럼 **서류 평가 없이 코딩테스트로 대체**하는 회사도 존재 (한국금융경제신문). 회사별 서류 비중이 크게 다르므로, 지원처 트랙을 먼저 확인해야 함.

**③ 프로젝트 적정 개수** — 소스마다 숫자 다름
- 3~4개(잡코리아, velog @sammy1), 3~5개(서치라이트 신입/주니어), 5개 안팎~최대 10개(이랜서·서치라이트 시니어), 최대 5개(링커리어).
- 공통 합의는 "많이가 아니라 완성도". 연차·JD 관련성에 따라 조정. (편집자 정리)

**④ STAR vs PAAR** — 경합하는 프레임
- STAR(velog @sammy1, 링커리어)가 전통적 표준. 서치라이트는 Action보다 Analyze(대안 검토)를 강조하는 PAAR을 제안. 둘은 배타적이지 않고, 백엔드·경력직일수록 "선택 근거(Analyze)"를 명시하는 쪽이 유리.

> **통념 표시**: 아래는 널리 통용되지만 이번 수집 소스에서 명확한 출처로 뒷받침되지 않은 일반론이다.
> - (통념) "이력서는 최신순 역순으로 배열한다" — Wonny Log가 경험 섹션 최신순을 언급하나 전 직무 일반 규칙으로 단정할 근거는 약함.
> - (통념) "채용은 결국 사람 추천(레퍼럴)이 가장 강력하다" — 수집 소스에 근거 없음.

## 5-1) 2026-08-19 보강 — 추가 리서치 3소스 (원티드 데이터·이력서 스터디·토스)

**정량 근거 2건 (원티드 자체 데이터, 소스 17)**
- 성과를 수치로 정량화한 이력서의 합격률이 **+13%** — "수치화하라"의 몇 안 되는 실측 근거.
- 채용담당자는 **자기소개서보다 경력기술서를 먼저 본다** (서치라이트, 소스 3) — 문서 투자 우선순위의 근거.

**역할 칸 서식** (서치라이트, 소스 3)
- 프로젝트당 5항목: 프로젝트명 · 기간(YYYY.MM~YYYY.MM) · 성과(KPI 수치) · 역할 · 기술/툴.
- 역할은 문제 해결·생산성·의사소통 3관점에서 **명사형 종결로 3~5줄 넘버링**. (우아한형제들 3관점과 별개 프레임 — 이쪽은 서식까지 지정)

**이력서 스터디 실전 교훈** (재그지그, 소스 18)
- 반복 지적 3종이 사실상 전부다: **너무 추상적 / 너무 장황 / 근거 부족.**
- 개선의 핵심은 추가가 아니라 **과감한 삭제** (실전 목표 예: 4장→3장, 자기소개 5문단→3문단).
- 핵심 경험 딱 3개 + 심화 내용은 링크로 분리.

**토스 관점** (inthiswork 정리, 소스 19)
- 경험 나열이 아니라 **임팩트와 러닝 포인트**. 프로젝트의 **개발 동기(왜 만들었나)**를 기재 — 고객 문제에서 출발했는지를 본다.
