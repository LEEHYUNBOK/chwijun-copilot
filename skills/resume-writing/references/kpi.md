## 0. KPI는 네 층이다 — 섞으면 안 된다

이력서에서 가장 흔한 사고가 층을 섞는 것이다. 서비스 지표를 개인 성과처럼 쓰거나, 팀 배포 통계를 본인 실적으로 올리는 것.

| 층 | 무엇을 재나 | 대표 체계 | 이력서에서 |
|---|---|---|---|
| **서비스** | 시스템이 잘 도는가 | SLI / SLO / Error Budget | 내가 만든 개선의 전후 |
| **전달** | 팀이 얼마나 빨리·안전하게 내보내는가 | **DORA 4 Keys** | 팀 수치임을 밝히고 기여 분리 |
| **AI** | AI를 넣고 무엇이 바뀌었나 | AI Capabilities Model · 채택/코드비중 | **2026년 신규 축. 아래 §2** |
| **개인·팀** | 사람이 잘 일하는가 | SPACE | 직접 쓰지 않는다. 면접 답변용 |

**서비스 지표가 이력서에서 제일 강하다.** 내가 손댄 범위가 명확하고 전후 비교가 되기 때문이다.

## 1. DORA 4 Keys 🟢

Google의 DevOps Research and Assessment. 소프트웨어 전달 성능의 사실상 표준이다.

| 지표 | 정의 | 방향 |
|---|---|---|
| **Deployment Frequency** | 프로덕션 배포 빈도 | 높을수록 |
| **Lead Time for Changes** | 커밋 → 프로덕션까지 걸린 시간 | 짧을수록 |
| **Change Failure Rate** | 배포 중 **즉시 조치(핫픽스·롤백)가 필요했던 비율** | 낮을수록 |
| **Failed Deployment Recovery Time** | 장애 발생 후 복구까지 (구 MTTR) | 짧을수록 |

### 벤치마크 (2025-09 DORA 리포트 기준) 🟡

| 지표 | 분포 |
|---|---|
| 배포 빈도 | 온디맨드(하루 여러 번) **16.2%** · 하루~주 1회 21.9% · **월 1회 미만 23.9%** |
| 리드 타임 | 1시간 미만 **9.4%** · 하루~1주 31.9% · **1주 초과 43.5%** |
| 복구 시간 | 상위권 평균 **약 34분** |

**DORA 4개만으로는 2026년에 부족하다** 🟡 — AI가 생성한 코드의 영향을 추적하지 못한다. 4 Keys는 여전히 유효하되, 아래 AI 축과 함께 봐야 한다.

### ⚠️ 배포 성공률 ≠ Change Failure Rate

가장 흔한 오용이다. 파이프라인 성공률은 **빌드·배포 작업이 통과했는가**이고, CFR은 **배포된 변경이 프로덕션에서 문제를 일으켜 조치가 필요했는가**다. 배포가 100% 성공해도 그 코드가 장애를 냈으면 CFR에 잡힌다.

CFR을 안 재고 있으면 "배포 성공률"이라고 정확히 쓴다. 환산하지 않는다.

## 2. AI 시대의 지표 — 2026년 판이 바뀌었다

### 2-1. 처리량은 올랐고 안정성은 무너졌다 🟡

2026년 텔레메트리가 일관되게 같은 방향을 가리킨다.

| 지표 | 변화 |
|---|---|
| AI 생성 코드 비중 | Q1 34% → **Q2 50% 초과** |
| 저자당 PR | 전년 대비 **+20%** |
| 개발자 절약 시간 | 주 **4~6시간** |
| **PR당 인시던트** | **+23.5%** |
| **Change Failure Rate** | **+30%** |
| PR 크기 | **거의 2배** |
| 변경 확신도 | **-6.1%** |
| 개발자 경험 지수 | **하락** |

병목이 사라진 게 아니라 **downstream으로 이동**했다. 코드는 빨리 나오는데 사람이 리뷰하는 지점에서 막힌다. PR 리뷰 시간이 급증한다.

DORA 2025판의 표현이 정확하다 — **AI는 증폭기다.** 잘 하는 조직은 더 잘하게, 망가진 조직은 더 망가지게 만든다.

> 면접에서 AI 활용을 말할 때 이 트레이드오프를 모르면 "생산성 올랐습니다"에서 끝난다. **속도를 얻고 무엇을 내줬는지** 말할 수 있어야 한다.

### 2-2. DORA AI Capabilities Model — 7가지 역량 🟢

2025-09에 별도 발간. "AI를 도입했다"가 아니라 **"AI가 효과를 내는 조건"**을 정리한 것이다.

1. **명확히 공표된 AI 방침** — 모호한 가이드라인은 채택률과 신뢰를 떨어뜨린다
2. **건강한 데이터 생태계**
3. **AI가 접근 가능한 내부 데이터** — 사내 문서·코드베이스·스타일 가이드를 붙이면 범용 어시스턴트가 전문가가 된다
4. **탄탄한 버전 관리**
5. **작은 단위로 일하기**
6. **사용자 중심**
7. **양질의 내부 플랫폼** ← **모델에서 가장 큰 증폭 요인**

7번이 핵심이다. 개인의 AI 생산성이 조직 성과로 바뀌려면 자동화된 "포장도로"가 있어야 하고, 없으면 개인 이득이 downstream 병목에서 전부 소실된다.

### 2-3. AI 축에서 실제로 재는 것 🟡

2026년 기준 벤치마크는 최소 5개 중 3개를 본다.

| 차원 | 지표 |
|---|---|
| 채택 | AI 도구 사용률, 일 사용 빈도 |
| **AI 코드 비중** | 전체 대비 AI 생성/보조 코드 비율 |
| 복잡도 보정 속도 | 난이도 감안한 처리량 |
| 코드 품질 | 리뷰 반려율, 재작업률(Rework Rate) |
| ROI | 절약 시간 대비 비용 |

측정의 출발점은 하나다 — **AI 보조 기여와 사람 단독 기여를 분리해서 재라.** 섞으면 상관관계만 남고 인과를 못 만든다.

### 2-4. AI 활용이 「우대」가 아니라 「자격요건」이 됐다 🟢

2026년 국내 공고 원문에서 직접 확인된 예다. 추세 주장이 아니라 실측이다.

| 회사 | 위치 | 문구 |
|---|---|---|
| **당근** 나의당근 | **필수요건** | "AI·LLM을 활용해 개발 생산성을 높이거나 새로운 방식의 문제 해결을 시도해본 경험" |
| **라인** LINE Pay Server | **자격요건** | "AI 기반 개발 도구를 실무에 활용한 경험" |
| **무신사페이먼츠** Release & IT Ops | **자격요건** | "AI 도구를 적극적으로 활용해본 경험이 있으며, 업무에 응용하는 데 거부감이 없으신 분" |
| **NHN Dooray** 백엔드 | **필수요건** | "새로운 기술(AI 등)을 학습하고 서비스에 적용하는 데 거부감이 없으신 분" (우대: LangChain·LangGraph) |

**"LLM을 붙여봤다"와 "LLM 출력을 신뢰하지 않는 구조를 만들었다"는 완전히 다른 서술이다.** 앞은 누구나 쓰고, 뒤는 코드가 있어야 쓴다.

## 3. SLI / SLO / Error Budget 🟡

서비스 층의 언어. SRE·플랫폼 직무 공고에서 그대로 나온다.

```
SLI  측정값          — p99 응답시간, 성공률, 가용성
SLO  목표            — "p99 < 300ms를 30일 중 99.9%"
Error Budget  허용 실패  — 99.9% 목표 = 0.1%까지는 써도 되는 예산
```

Error Budget이 실무에서 중요한 이유는 **"안정성 대 속도"를 감정이 아니라 숫자로 정하기 때문**이다. 예산이 남으면 배포를 밀고, 다 쓰면 기능을 멈추고 안정화한다.

무신사 테크블로그에 2주간 3개 서비스에 SLO 27개·모니터 54개를 세운 사례가 공개돼 있다 🟡 — 국내 사례라 인용하기 좋다.

## 4. 경력기술서에 실제로 쓰이는 백엔드 지표 🟡

### 성능
| 지표 | 서술 예시 |
|---|---|
| 응답시간 p50/p95/p99 | `API 평균 응답 420ms → 180ms` |
| 처리량(TPS/RPS) | `동시 500 부하에서 오류 0` |
| 배치·잡 소요 | `배치 30분 → 12분` |
| 쿼리 수 / 슬로우 쿼리 | `N+1 제거로 쿼리 143 → 4` |

### 안정성
| 지표 | 서술 예시 |
|---|---|
| 장애 건수·빈도 | `동일 유형 문의 주 15건 → 4건` |
| 오류율 | `결제 실패율 2.1% → 0.3%` |
| 복구 시간 | `장애 인지~복구 40분 → 8분` |
| 롤백 횟수 | |

### 전달
| 지표 | 서술 예시 |
|---|---|
| 배포 빈도·소요 | `배포 20분 절감` |
| 파이프라인 성공률 | ⚠️ CFR과 구분해 표기 |
| 리드 타임 | |

### 품질
| 지표 | 서술 예시 |
|---|---|
| 테스트 커버리지 | `핵심 도메인 18% → 54%` |
| 코드 리뷰 반영률·PR 수 | |
| 재작업률 | AI 시대에 비중이 커진 지표 |

### 운영 효율
| 지표 | 서술 예시 |
|---|---|
| 자동화로 없앤 수작업 시간 | `수작업 3단계 → 1단계` |
| 온보딩 시간 | `신규 기관 온보딩 수 일 → 수 시간` |
| 인프라 비용 | |

**주니어~미들은 매출이 아니라 운영 지표를 본다** 🔴 — 매출은 기여 분리가 안 되고 검증도 안 된다.

## 5. SPACE 🟢 — 이력서에 쓰지 말고 알고만 있기

2021년 Forsgren 외 발표. Satisfaction · Performance · Activity · Communication · Efficiency 5개 축.

핵심 주장은 **"개발자 생산성은 단일 지표로 환원되지 않는다"**이다. 커밋 수·라인 수 같은 Activity 하나만 보는 평가를 반박하려고 만들어진 틀이다.

**2026년에 이 틀이 더 중요해졌다.** AI가 Activity 지표(PR 수·커밋 수)를 쉽게 부풀리기 때문이다. PR이 20% 늘었는데 인시던트가 23.5% 늘었다면 Activity만 보는 평가는 정확히 반대 결론을 낸다.

## 6. 본인 수치 매핑하기

`<wiki_path>/프로필.md`의 대표 작업 수치를 1~5장의 층(전달·안정성·성능·품질·AI·운영)에 대입해 표로 만든다. **어느 칸이 비어 있는지가 이 표의 요점이다** — 비어 있는 칸은 지어내지 말고 ❌ 미측정으로 두고, 팀 수치는 본인 기여를 분리할 수 있을 때만 쓴다.

## 7. 쓰면 안 되는 것

| 금지 | 이유 |
|---|---|
| 커밋 수·코드 라인 수를 성과로 | SPACE가 정면 반박. AI 시대엔 더 무의미 |
| 커밋 작성자·git blame을 기여도 근거로 | AI가 코드를 쓴다. 기여는 기획·검증·개선 판단의 주체로 판정하고, 참여도는 본인 진술로 확정 |
| "AI로 생산성 N% 향상" | 2026 실측은 처리량↑ 안정성↓다. 한쪽만 말하면 모르는 것으로 읽힌다 |
| 팀 배포 통계를 본인 실적처럼 | 팀 수치는 본인 기여를 분리 못 하면 못 쓴다 |
| 배포 성공률 → CFR 환산 | 다른 지표다 |
| 기준 없는 퍼센트 | 무엇을 어떻게 쟀는지 못 쓰면 삭제 |
| 40명·500명을 "대용량" | 자릿수가 다르다 |

## 8. 프로젝트에 "용량 한 줄" — 트래픽 가정 · 부하 검증 · 서버 스펙 🟡

대부분의 지원자는 "만들고 배포했다"에서 끝나고 이력서엔 문제 해결만 쓴다. 프로젝트마다 **이 도메인이 감당할 트래픽을 가정 → 부하로 검증 → 그에 맞춰 서버를 운용**을 한 줄 붙이면 용량 설계 사고가 드러난다. 실무는 예상 트래픽을 잡고 부하 테스트가 통과해야 배포하기 때문이다.

골격: `[도메인] 예상 피크 [가정치] → 부하 테스트 [측정 TPS·성공률] → 서버 [스펙]`

⚠️ **측정과 가정을 반드시 구분한다 — §7과 직결.**
- 가정치는 "예상·목표"로 **라벨한다.** 잰 적 없는 TPS를 측정값처럼 쓰면 면접에서 무너진다.
- 가정에서 끝내지 말고 **부하 테스트로 실측**한다(jMeter·k6). 실측 한 줄이 가정 열 줄보다 강하다.
- 프로덕션 실사용 TPS가 낮으면(B2B·사내도구) 실사용 수치는 빼고 **부하 테스트 용량 여유**로만 쓴다. 낮은 실측을 규모처럼 포장하지 않는다.
- 서버 스펙이 대외비면 자릿수·구조만("2AZ 오토스케일링 그룹") 쓰고 인스턴스 타입·수는 쓰지 않는다.

출처: 유튜브 개발자 이력서 팁(2026). 원 팁은 "TPS·서버 스펙을 **가정**해 한 줄"이지만, 가정만 쓰는 건 위험 — 실측·라벨·대외비 가드레일을 얹어 채택. 🔴
