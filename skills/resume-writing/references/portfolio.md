## 0. 포트폴리오는 자랑집이 아니라 사용설명서

"내가 이것도 했고 저것도 했다"를 늘어놓는 문서가 아니다.
**"나를 어떤 일에, 어떻게 쓰면 좋은지"를 알려주는 설명서**에 가깝다.

읽는 사람이 확인하려는 건 세 가지다.

1. 문제를 스스로 발견하고 정의할 수 있는가
2. 나름의 가설을 세우고, 한 번이라도 실행해 봤는가
3. 그 과정에서 무엇을 배웠고, 다음엔 어떻게 더 잘하려 하는가

프로젝트를 넣기 전에 그 프로젝트가 이 셋을 얼마나 보여주는지 먼저 본다. 셋 다 약하면 분량만 잡아먹으므로 빼는 게 낫다.

### 경력자에게 어떻게 적용되나

이 프레이밍 자체는 연차와 무관하다. 오히려 경력자는 "검증된 영역"을 정확히 그려줘야 하므로 사용설명서 성격이 더 강해진다. 달라지는 건 강조점이다.

| | 신입 | 경력자 |
|---|---|---|
| 무게중심 | 사고 과정 | 사고 과정 **+ 재현 가능한 성과** |
| 가설 | 틀려도 괜찮다 | 틀렸다면 **언제 알아챘고 어떻게 회수했는지**까지 |
| 소재 | 크기는 상관없다 | **책임 범위와 임팩트**가 드러나는 것 |
| 실패 | 배운 점으로 마무리 | 배운 것을 **다음 프로젝트에 적용한 증거**까지 |
| 협업 | 팀과 내 몫 구분 | 구분 + **내가 팀에 남긴 것**(문서·규칙·도구) |

## 1. 프로젝트 서술 5단 구조

성과를 거창하게 쓰는 것보다, **문제를 어떻게 풀어갔는지**에 무게를 실으면 완성도가 확 올라간다.

```
1. 한 줄 요약    어떤 상황에서 / 무엇을 / 왜 했는지.  2~3줄
2. 문제의식      어떤 장면·데이터에서 문제를 느꼈나
3. 가설          "이렇게 하면 이렇게 될 것이다" + 그렇게 판단한 근거
4. 실행          쓴 도구, 시도한 방법, 막혔던 지점과 푼 방법
5. 결과 & 배운 점 수치 또는 전후 변화 + 다음엔 무엇을 다르게 할 것인가
```

**2번 문제의식** — "불편해 보였다"는 근거가 아니다. 관찰·수치·사례 중 하나는 있어야 한다.
> ❌ 사용자들이 불편해할 것 같았습니다.
> ✅ CS 문의 로그를 보니 3개월간 동일 문의가 214건이었고, 그중 절반이 같은 화면에서 발생했습니다.

**4번 실행** — 내가 직접 한 일과 팀이 함께 한 일을 구분해서 쓴다. 구분 자체가 협업 스타일을 드러낸다. 실행에는 코드만이 아니라 판단이 들어간다 — AI에게 무엇을 시켰고, 출력을 어떤 기준으로 검증·기각했는지가 곧 실행 서술이다.

**5번 배운 점** — 여기서 끝내지 말고 "다음엔 무엇을 다르게 할 것인가"까지 간다. 회고 능력과 성장 가능성이 여기서 보인다.

### 경력기술서와 무엇이 다른가

같은 프로젝트를 써도 문서 목적이 다르다.

| | 경력기술서 (`rule.md` 1-2) | 포트폴리오 |
|---|---|---|
| 답하는 질문 | **무엇을 했나** | **어떻게 생각했나** |
| 구조 | 맥락 → 기술 → 역할 → 한 일 | 요약 → 문제의식 → 가설 → 실행 → 결과·배움 |
| 분량 | 프로젝트당 1페이지 이내 | 프로젝트당 2~4페이지 |
| 개수 | 전부 | **3~5개만 골라서** |

포트폴리오는 전수 나열이 아니다. 깊게 파고들 수 있는 것만 고른다.

## 2. 가설 칸 채우는 법

`rule.md` 2장의 공식(문제 → 선택 → 결과 → 근거)에서 가장 자주 비는 칸이 여기다.
"선택"을 그냥 적으면 결정이 아니라 사실 기록이 된다. 가설 형태로 쓰면 사고 과정이 드러난다.

```
관찰:  무엇을 보고 문제라고 판단했나
가설:  X를 하면 Y가 개선될 것이다. 근거는 Z다.
검증:  어떻게 확인할 계획이었나 / 확인했나
결과:  맞았나, 틀렸나
```

- **"~일 것 같아서 해봤다"는 가설이 아니다.** 근거(Z)가 있어야 가설이다.
- **가설이 틀렸을 때가 더 좋은 소재다.** 맞은 이야기는 결과 자랑으로 끝나지만, 틀린 이야기는 "언제 알아챘고 무엇으로 갈아탔는지"까지 보여줄 수 있다. `rule.md` 1-3의 트러블슈팅 원칙과 같은 이유다.

## 3. 쓸 소재가 없을 때

원문은 신입 기준으로 네 갈래를 든다 — 학습 과정 정리 / 서비스 역기획·분석 / 일상의 작은 자동화 / 팀·동아리·수업 프로젝트. 요지는 **경험의 크기가 아니라 소재를 바라보는 시선**이다.

경력자가 부딪히는 벽은 다른 쪽이다. **"회사 일이라 공개할 수 없다."** 우회 경로:

| 경로 | 방법 |
|---|---|
| 사내 프로젝트를 일반화 | 절대 수치를 상대 수치로. "월 매출 12억" → "결제 실패율 절반으로" |
| 의사결정만 떼어내기 | 코드·화면을 못 보여줘도 **왜 그 구조를 골랐는지**는 쓸 수 있다 |
| 역기획 · 분석 리포트 | 경쟁 서비스나 오픈소스를 뜯어보고 개선안 제시. 연차가 있으면 깊이에서 차이가 난다 |
| 오픈소스 · 기술 글 · 발표 | 공개 결과물 자체가 증거다 |
| 실패한 프로젝트 사후 분석 | 신입은 못 쓰는 소재다. 왜 접었는지, 무엇을 놓쳤는지 |
| 사내에 남긴 것 | 문서, 컨벤션, 자동화 스크립트, 온보딩 가이드 — 개인 산출물보다 팀에 남은 게 더 세다 |

민감 정보는 지우되 **의사결정의 논리는 지우지 않는다.** 논리까지 지우면 남는 게 없다.

## 4. 읽는 사람의 머릿속

현업 리더는 포트폴리오를 보면서 속으로 이렇게 묻는다.

- 이 사람을 뽑으면 **어떤 일을 맡길 수 있을까**
- **스스로 문제를 찾아 움직이는 사람일까, 시키는 일만 하는 사람일까**
- 실수를 하더라도 **빨리 배우고 성장할 사람일까**

경력자에게는 하나가 더 붙는다.

- **지금 우리 팀에 없는 무엇을 가져오는가**

목표는 완벽한 문서가 아니다. **"이 사람이면 같이 일해보고 싶다"** 는 생각이 들게 만드는 것이다.

## 5. 수치가 없을 때 — `learning` · `improvements`

`rule.md` 2장의 공식은 **문제 → 선택 → 결과 → 근거**다. 결과 칸에 숫자가 들어가는 걸 전제한다. 그런데 측정을 못 한 건이 반드시 생긴다 — 개선 후 수치를 안 잰 장애, 원인 규명에 실패한 사건, "되냐 안 되냐"가 결과인 연동 이슈.

지금 구조에는 **그런 건을 쓸 자리가 없다.** 그래서 약하게 처리되거나 통째로 빠진다.

칸을 두 개 더 둔다.

```
issue         무엇이 터졌나
context       어떤 상황에서
solution      무엇을 어떻게 고쳤나
learning      ← 이 일에서 무엇을 알게 됐나 (결과 수치가 없을 때 이 칸이 결과를 대신한다)
improvements  ← 아직 못 한 것 / 다음에 할 것
```

### `learning` — 배움을 규칙 문장으로 쓴다

감상이 아니라 **다음에 적용할 규칙**이어야 한다.

> ❌ 많은 것을 배울 수 있었습니다.
> ❌ 임시조치의 위험성을 느꼈습니다.
> ✅ 임시조치에 만료 조건을 걸지 않으면 그게 다음 장애가 된다. 이후 우회 코드에는 제거 조건과 담당자를 주석으로 남긴다.

판별법 하나 — **그 문장만 떼어내 팀 위키에 올려도 말이 되는가.** 안 되면 감상이다.

### `improvements` — 미완성을 로드맵으로

"못 했다"가 아니라 "여기까지 했고 다음은 이것"으로 놓는 자리다. 숨기는 것보다 세다.

무신사처럼 **"프로젝트의 성공과 실패를 떠나"** 를 명문화한 곳에서는 이 칸이 특히 유효하다.

### 칸을 고정하면 빈 곳이 보인다

프로젝트마다 서술 형식이 다르면 무엇이 빠졌는지 알 수 없다. **모든 프로젝트에 같은 칸을 두고 전부 채운다.**

| 칸 | 답하는 질문 |
|---|---|
| `background` | 왜 만들었나 |
| `challenges` | 어려웠던 지점 |
| `responsibilities` | 내가 한 일 |
| `troubleshooting` | issue / context / solution / **learning** |
| `improvements` | 다음에 할 것 |
| `teamSize` | **인원 구성** — 단독인지 몇 인 팀인지 |

`teamSize`를 칸으로 두면 기여 범위를 안 밝히고 넘어갈 수가 없다. `rule.md` 3장의 "팀 성과를 내 성과처럼" 금지를 구조로 강제하는 방법이다.

## 6. GitHub 큐레이션 · 제출 형식

채용담당자는 링크가 있으면 실제로 들어가 본다. 정리 안 된 GitHub은 강점이 아니라 "관리되지 않은 인상"으로 감점 요인이다.

- **직무와 연결되는 레포 3~5개만 남긴다.** 정리 안 된 레포·실습 저장소는 private 처리
- **클론 코딩 레포는 걸지 않는다.** 통하는 것은 "왜 그 기술을 골랐나"가 담긴 문제 해결형 프로젝트
- 대표 레포 README에는 아키텍처 구조 · 내 기여 범위 · 기술 선택 이유를 담는다 — 코드 자체보다 이게 읽힌다
- 백엔드는 화면이 없으므로 성능 개선 · 장애 대응 · 운영 판단 서술이 포트폴리오다. 프로젝트당 2~3페이지씩 10장 넘게 만드는 건 과잉
- **제출은 PDF 기본 + 노션·GitHub 링크 병기.** 노션 단독 제출은 링크를 차단하거나 열지 않는 회사가 있어 위험

## 7. 포트폴리오 체크리스트

`rule.md` 8장에 더해서:

- [ ] 프로젝트를 3~5개로 추렸다 (전수 나열이 아니다)
- [ ] 각 프로젝트가 5단 구조를 다 채웠다 — 특히 **가설** 칸
- [ ] 문제의식이 관찰·수치·사례로 뒷받침된다
- [ ] 가설에 근거("왜냐하면")가 붙어 있다
- [ ] 내가 한 일과 팀이 한 일이 구분되어 있다
- [ ] 각 프로젝트가 "다음엔 무엇을 다르게 할 것인가"로 끝난다
- [ ] 가설이 틀렸던 사례가 최소 하나 있다
- [ ] 모든 프로젝트에 **인원 구성**(단독/N인)이 적혀 있다
- [ ] 수치가 없는 트러블슈팅은 `learning`으로 닫았다 — 감상이 아니라 규칙 문장으로
- [ ] 각 프로젝트에 `improvements`(다음에 할 것)가 있다
- [ ] 4장의 네 가지 질문에 이 문서만 보고 답할 수 있다
- [ ] 이 문서를 읽고 "무슨 일을 맡기면 되겠다"가 한 문장으로 나온다
